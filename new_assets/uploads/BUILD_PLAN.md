## Full end-to-end API audit — DONE (2026-09-02)

Requested explicitly before building a Postman collection and Swagger docs, since both are only worth building against a backend that's actually complete. Extracted the ground-truth route list straight from the NestJS boot log (`Mapped {...} route` lines) rather than trusting a hand-maintained list — **90 routes total**. Every GET route was hit with a real token and returned 200; every protected route returned 401 with no token and 403 for the wrong role (tested with the Employee-role user against org-admin-only routes); the PDF/Excel/logo binary endpoints were checked for correct `content-type`, not just status code. Mutation endpoints were exercised with real create/update/delete cycles (leave types, holidays, roles + clone, employees + Excel import, salary structures, statutory config, attendance, leave requests + decision, correction requests + resolve, user invites, org settings, SuperAdmin actions) — not just re-trusted from earlier sections.

This pass found and fixed **4 real bugs**, all only visible by actually calling the routes:

1. **`PATCH /statutory-config` 500'd whenever the `financialYear` query param was omitted** — `GET` on the same resource already defaulted it, `PATCH` didn't, so `undefined` hit Sequelize's `WHERE` clause directly. Worse, the default it now shares was itself wrong: hardcoded to April regardless of the org's actual configured `financialYearStartMonth` (a field that's explicitly editable via org settings). Fixed by deriving the default from the organization in both handlers.
2. **Rate fields on `StatutoryConfig` (`DECIMAL(5,4)`, stored as fractions like `0.12`) had no upper-bound validation** — passing `12` (a caller thinking in percent, not fraction) overflowed the column and crashed with a raw Postgres error instead of a clean 400. Added `@Max(1)`.
3. **`POST /users/invite` threw a 500 if the SMTP send failed**, after the user row was already created — silently orphaning an `INVITED` user the admin has no visibility into. `forgotPassword` already had this exact resilience pattern (try/catch, log, never throw); `invite` didn't. Now matches it.
4. **`POST /employees/import` crashed with an unhandled `TypeError` if no file was attached** (`@UploadedFile()` returns `undefined`, `.buffer` threw). Added an explicit check → clean 400. Also used this to actually exercise the happy path for the first time with a real `.xlsx` file built via `exceljs` — confirmed a row parses and lands in Postgres correctly, since this endpoint had never been tested with a real upload before.

All fixes verified against the live server (both the crash *and* the correct behavior after the fix), full `tsc`/`jest`/`nest build` chain re-run clean, test artifacts removed from the database afterward. **Verdict: backend is complete.** Proceeding to Swagger + Postman collection per user request.

Every controller got `@ApiTags(...)` for sidebar grouping (24 tags, one per resource) — checked that all 90 operations actually carry a tag, not just the controllers.

While documenting the two file-upload endpoints (`POST /employees/import`, `PATCH /organizations/current/logo`) — `FileInterceptor` alone doesn't produce an OpenAPI schema, needed explicit `@ApiConsumes('multipart/form-data')` + `@ApiBody(...)` — found the **same missing-file crash bug in the logo upload** as the one just fixed in the employee import (`file` was typed as required but NestJS passes `undefined` when nothing's attached, so `.size` access inside `OrganizationsService.uploadLogo` threw an unhandled TypeError). Fixed identically: optional param + explicit `BadRequestException` guard, verified live (400 now, not 500).

Served at `GET /api-docs` (UI) and `GET /api-docs-json` (raw OpenAPI document) — confirmed by fetching the JSON directly and checking operation count (90), tag count (24), and that DTO schemas resolve correctly, not just that the server boots without error.

## Postman collection — DONE (2026-09-02)

`docs/Payroll-SaaS-API.postman_collection.json` — generated programmatically from the validated OpenAPI document rather than hand-built, so its 90 requests, DTO-derived example bodies, and tag-based folders (24, matching Swagger) stay a direct reflection of the real API rather than drifting out of sync. Collection-level bearer auth (`{{accessToken}}`), with the 5 public auth routes overridden to no-auth. Path parameters resolved to semantic collection variables (`{{employeeId}}`, `{{roleId}}`, `{{payrollRunId}}`, etc.) built against the *actual* OpenAPI path list, not assumed — cross-checked every `{param}` in the spec by hand before writing the mapping table. Within each folder, requests are ordered Create → List → Get-by-ID → Update → Action → Delete so a top-to-bottom run is usable, not alphabetical. `testEmail`/`testPassword` collection variables drive login once and every other request rides on the captured token; `POST` "create" endpoints auto-capture their new resource's ID into the matching collection variable for later requests in the same folder to reuse.

**This was actually run, not just generated.** Installed `newman` (Postman's CLI runner) and executed the full 90-request collection against the live server multiple times, fixing what it found each round:

- Two generator bugs caught by a real run, not code review: `POST /auth/register`'s nested `organization`/`admin` object body was silently empty (the generator didn't recurse into `$ref` sub-schemas), and `refreshToken` in `POST /auth/refresh` got a garbage placeholder instead of referencing the token `login` had just captured (no fields other than `...Id`-suffixed ones were recognized as "reuse this variable"). Both fixed in the generator and re-verified.
- One collection-design bug: cloning a role in the `Roles` folder was overwriting the collection's `roleId` variable with the *clone's* id, so the folder's own cleanup step deleted the wrong role and orphaned the original. Fixed by not re-capturing `roleId` on clone.

**Four more real backend bugs surfaced by the live run** (same missing-validation pattern as the earlier audit, just not exercised until an actual sequential run hit them):

5. **`POST /roles/:id/clone`** took the new name via `@Body('name') name: string` with no DTO at all — not just unvalidated, *unparsed*. A missing body silently became `undefined`, which Sequelize then tried to insert into a `NOT NULL` column, crashing with a raw `SequelizeValidationError` instead of a 400. Added a proper `CloneRoleDto`.
6. **`POST /auth/register` didn't check for an existing email before inserting** — unlike `UsersService.invite()`, which already does this correctly. A duplicate registration crashed with a raw Postgres unique-violation error instead of a clean 409. Added the same existence check `invite()` already uses.
7. **`GET /payslips`, `GET /salary-structures`, `GET /loans-advances`** all filter by an `employeeId` query param typed as `@Query('employeeId') employeeId: string` — a compile-time-only claim NestJS doesn't enforce at runtime. Omit the param and Sequelize gets a literal `undefined` in a `WHERE` clause and crashes. Same root cause across all three, same fix: `@Query('employeeId', ParseUUIDPipe)`, which cleanly rejects missing or malformed values with a 400.
8. **`GET /reports/joining-exit`** took `from`/`to` as raw unvalidated query strings straight into a Sequelize `Op.between` date-range filter — empty or malformed input reached Postgres as `"Invalid date"` and crashed there instead of being rejected earlier. Added a `JoiningExitReportQueryDto` with `@IsDateString()`.
9. **`LeaveTypesService.remove()` had no usage guard at all** — unlike `RolesService.remove()`, which correctly blocks deleting a role that still has users assigned. Since `leave_requests.leaveTypeId` has a real FK constraint, deleting *any* leave type that was ever actually used crashed with a raw `SequelizeForeignKeyConstraintError` instead of a clean, actionable message. Added the same kind of guard the roles service already has: count referencing leave requests first, `403` with a clear message if any exist.

After each fix: rebuilt, restarted against the real Neon DB, re-ran the specific failing request to confirm the fix, then re-ran the *entire* 90-request collection again. The final full run came back with **zero 500-level responses** — every remaining non-2xx is an intentional 400/403/404/409/401 for a genuinely invalid request. Test artifacts created by the newman runs (roles, orgs, leave types/requests) were removed from the database afterward using the same direct-cleanup approach as the manual audit, since none of these resources have delete endpoints available for every case (e.g. no organization-delete endpoint, by design).

**Net count for this whole "check end to end" request: 9 real backend bugs found and fixed**, all of them the same underlying pattern — a code path that assumed valid input and let a raw database error leak out as an unhandled 500 instead of validating first and returning a clean 4xx. None of them were found by reading code; all of them were found by actually calling the endpoint, live, against the real database — consistent with how every other section of this build has been verified throughout.

## Frontend bug fix — onboarding checklist disappearing after re-login (2026-09-03)

Real bug, reported by the user directly: after finishing registration the onboarding checklist showed correctly ("5 steps incomplete"), but logging out and back in landed straight on the dashboard with no way back to it. Root cause: the checklist was only ever reachable via the one-time post-registration redirect — Phase 1 never built the "reappears via a Setup nav item until complete" part the original `UI_UX_SPEC.md` (§3) actually calls for, so completing that spec item was simply missed.

Fixed by extracting the completion-check logic (was inline in the onboarding page) into a shared `useOnboardingStatus()` hook, and adding a persistent "Setup" nav item (badge showing e.g. "2/5") that's visible whenever onboarding is incomplete, gated behind `settings.edit` so it only queries for users who'd plausibly act on it — an Employee-role user hitting `GET /employees` etc. from this hook would just 403 for no reason. Completion is cached in `localStorage` once true (it's a one-way transition — an org doesn't "un-complete" onboarding by later deleting its only employee) so the underlying 5 queries stop firing entirely for orgs that finished onboarding long ago, not just get re-fetched-and-ignored every session.

## Frontend — Phase 2 (Workforce core) — DONE (2026-09-03)

Employees (list/create/edit/detail with tabs/Excel import), Users (list/invite/role-change/status-toggle), Roles (list + live two-panel editor). One deliberate deviation from the written route map: `roles/[id]` was planned as a separate route, but built instead as `/roles?roleId=...` — a single page where clicking a role in the left list updates the right-hand editor without a page navigation, which is what the prototype's two-panel layout actually does and a route split would have broken.

Two real bugs found while building against the live backend, not from code review:

- **`apiClient` couldn't handle `DELETE /roles/:id`'s actual response shape.** It only special-cased an empty body for HTTP 204; this endpoint returns 200 with a genuinely empty body (the service returns `void`, NestJS doesn't override the default 200), so `res.json()` would have thrown a JSON parse error on every role deletion. ## Invite flow redesign: auto-generated temp password (2026-09-03)

Root cause of "no email ever arrives" confirmed from live server logs: Gmail rejects the SMTP credentials (`535 Bad Credentials`), and `SMTP_USER=payroll_saas` in `.env` isn't even a full email address, which Gmail SMTP requires — needs the user's own Gmail App Password, not something fixable from here.

Separately, redesigned the invite UX per explicit request: `UsersService.invite()` now generates a real, crypto-secure temporary password (`generateTempPassword()` — excludes visually-ambiguous characters like `0/O`, `1/l/I` since it's read off an email and typed by hand) instead of a placeholder hash + 7-day set-password link. The invited user logs in with it immediately — `AuthService.login()` no longer rejects `INVITED` status — and the login response carries `mustChangePassword: true` (new field on `AuthenticatedUser`, flows straight through the JWT since `TokenService` just serializes the whole interface). `AuthService.changePassword()` now flips `INVITED → ACTIVE` on success, mirroring exactly what `resetPassword()` already did for the old link-based flow — same transition, different entry point. The token-link mechanism (`forgotPassword`/`resetPassword`) is untouched and still the only recovery path if an invite email genuinely never arrives.

Since SMTP is broken independent of any of this, `invite()` also returns the plaintext temp password once in its response (`{ user, temporaryPassword }`) — the frontend's invite dialog shows it with a copy button as an explicit manual fallback, since that's the only way to actually test this today.

Frontend: `RequireAuth` now redirects to a new `/change-password` page whenever `user.mustChangePassword` is true, blocking every other route until it's cleared (mirrors the existing `requireSuperAdmin` redirect pattern in the same file). Since `changePassword` revokes refresh tokens server-side, the change-password page re-authenticates with the new password immediately after (using `displayEmail` already held in `AuthContext`) rather than trying to patch the existing session's tokens in place.

Verified the complete transition against the live backend, not just individually: invited a real test user → confirmed `temporaryPassword` in the response → logged in with it (previously would have 401'd, now succeeds with `mustChangePassword: true`) → called `change-password` with it as `currentPassword` → re-logged in and confirmed `mustChangePassword: false` and `status: active` in the database. Cleaned up the test user afterward (needed to also clear its own `audit_logs.actorUserId` FK reference first — `changePassword`'s audit record logs the user as the actor of their own password change).

## Post-launch bug fixes, rebrand to Emplora, Redux migration, theme toggle (2026-09-04)

First real usage pass after the frontend build completed surfaced a bundle of fixes, sequenced as phases so each lands independently verified.

**Phase 0 — bug fixes.** Both reported React "controlled/uncontrolled" warnings (Select on `/payslips`, Checkbox on `/settings`) trace to the same root cause: a `useForm({ values: x ? {...} : undefined })` or bare `useState<string | undefined>(undefined)` starts a bound value at `undefined` on first render, then becomes defined once a query resolves or a selection is made — BaseUI treats that as switching from uncontrolled to controlled. ## Design principle to hold onto throughout

Nothing in this schema or UI should be hardcoded to "Meridian Apparels" or one client's rules — organization branding (logo, name), statutory rates, and pay-cycle settings all live in config tables. That's not gold-plating: it's what turns this from "software for one client" into a product you can sell to the *next* company that needs payroll software, with zero rebuild. Worth keeping in mind when a client asks for something oddly specific — build the general version, configure it per-org, don't fork the code.
